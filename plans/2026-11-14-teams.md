## 1. Where I think the design is wrong, missing or too heavy

**Wrong (it would not work as written)**

1. **The guard hook cannot enforce path ownership on its own.** It sees `Edit`/`Write` paths, but a
   session can write anywhere through Bash (`sed -i`, `>`, `cp`, `git checkout other -- path`), and
   shell cannot be parsed reliably. The guard stays the drift layer (and catches the common shell
   forms); the wall is the CI ownership check plus branch protection.
2. **Nothing on GitHub tells teams apart.** Every session pushes and opens issues as you, with one
   `gh` login. CI can prove "this PR touches only one team's paths and declares that team"; it cannot
   prove "this PR came from that team's session". Real per-team identity means a GitHub App or
   machine user per team. I propose deferring that and saying so in TEAMS.md.
3. **An environment variable is spoofable from inside Bash.** `FACTORY_TEAM=frontend ticket.sh ...`
   would let backend speak as frontend. Hooks are safe (they inherit the launch environment, which the
   agent cannot change), scripts are not. Fix: scripts require the env var **and** that they run in
   that team's registered worktree, and the guard blocks any command that assigns `FACTORY_TEAM` or
   `FACTORY_ALLOW_SELF_EDIT` or touches another team's worktree.
4. **Worktrees split the live state.** `emit-event.sh` and `telemetry.sh` write to the *worktree's*
   `.factory/`, so four sessions would produce four event logs and the control room would see one.
   Fix: every script resolves the main checkout through `git rev-parse --git-common-dir` and writes
   shared state there. (This is also a latent bug for anyone using worktrees today.)
5. **`claude -w` is unusable with this guard.** It creates worktrees under `.claude/worktrees/<name>`,
   and hooks keep `CLAUDE_PROJECT_DIR` at the main checkout, so every edit's relative path starts with
   `.claude/` and the guard blocks it. The launcher creates worktrees itself with `git worktree add`
   outside the repo and starts `claude` inside them.
6. **Planning files cannot live in the leads' worktrees.** Each worktree is on its own branch, so a
   position written in one is invisible to the others and the transcript would fork. Planning lives in
   the main checkout on a `planning/<cycle>` branch and is written only through scripts.
7. **The orchestrator cannot "watch" anything.** A Claude session acts only when prompted. Stall,
   deadlock and budget detection must be a script on a timer that rings the orchestrator only when it
   finds something. Cost when quiet: zero tokens.
8. **CI does not enforce the tier today, only the path rules.** The spec's `risk_floor` and the
   reviewer's `RISK` are applied only by the foreman's choice to enable auto-merge. "Security can raise
   any tier" is not mechanical until CI takes the maximum of path rules, spec floor, review and security
   report. I will add that (it strengthens a gate).

**Missing**

9. **The existing scripts have no tests.** "Test every script the way the existing ones are tested"
   has nothing to copy. I will add `factory/tests/` (plain bash, since bats is not installed), backfill
   tests for the four existing scripts, and run them in CI.
10. **FEATURE.md has two writers** (research writes acceptance criteria, the orchestrator writes links
    and status), which breaks path ownership. Split: research owns `features/<id>/acceptance.md`;
    `FEATURE.md` is generated by a script from it plus work items, tickets and e2e results.
11. **Contracts owned by nobody still need a first author.** Producing teams draft them during planning
    (backend: API; database engineer: data model; designer: design system and screens) as attachments to
    their positions. On approval a script promotes the accepted drafts into `contracts/`. After that,
    only contract-change tickets.
12. **Tickets live on GitHub, but the record must be a file.** Every ticket action also writes an event,
    and integration snapshots the feature's tickets into `features/<id>/tickets.jsonl`, committed.
13. **GitHub-runner automation does not fit team mode.** A runner session has no team identity.
    `factory.yml` stays for single-team factories; in team mode it ignores team-labelled issues.

**Too heavy**

14. **A full meeting for a small feature costs more than the feature.** Positions, two discussion
    rounds, specialist review and decisions are roughly 15 to 25 lead turns plus specialists before any
    code. On Max 5x that is a real slice of a 5-hour window. Add a **single-team cycle**: when the
    brief needs one team, skip positions and discussion; the orchestrator drafts a short DECISIONS.md;
    security joins only at R2 or above; you approve. And a cycle convenes only the teams its brief needs.
15. **Same-model agreement is not solved by blind positions alone.** Four instances of one model share
    priors. Mitigations: different models (orchestrator Opus, leads Sonnet), every position must contain
    "what I would object to in this brief", and security is adversarial by charter. Optionally, for R2
    cycles, a second-vendor read of DECISIONS.md (Codex is installed). That is opt-in, not default.

## 2. Transport: files are the channel, herdr is the doorbell

| Option | What I found | Verdict |
|---|---|---|
| **herdr** 0.9.5 (verified on this machine) | `pane split --cwd --env` → `agent start <name> --kind claude --pane <id> -- <claude args>` → `agent prompt <name> <text> --wait` → `agent wait --until idle,blocked,done` → `agent read --source recent-unwrapped`. Detects Claude's state from the screen (`idle, working, blocked, done, unknown`); socket API has `events.subscribe` / `events.wait`. Names `[a-z][a-z0-9_-]{0,31}`. | **Use**, for launch, nudges, state and reading output. |
| Claude Code cross-session messaging | Generally available (v2.1.224+), per-session socket. Not documented as persisted, no hook fires on send or receive, and the model decides when to use it. | **Turn off, without denying the tool.** `crossSessionInbound: "refuse"` in the project's `.claude/settings.json` ("from project or local settings, `refuse` applies over every other source"), so every factory session, worktrees included, drops inbound peer messages. `ListAgents` is denied. `SendMessage` stays allowed because "denying `SendMessage` also removes messaging to subagents". |
| Agent teams | Experimental flag, one team per session, mailbox in `~/.claude/teams/` (outside the repo), panes only via tmux or iTerm2. | No. |
| Background sessions (`--bg`, `claude agents`) | Research preview, no panes. | No. |

**Rule:** herdr only ever delivers a fixed doorbell such as `New items for you: run /inbox`. It never
carries content. Content travels through scripts into files (the transcript, dispatch records) or
GitHub issues (tickets), and every one of those writes an event. If herdr is down, leads run `/inbox`
themselves and nothing else changes.

Team rosters:
- **Research:** spec-writer, researcher, evidence-reviewer.
- **Frontend:** designer, spec-writer, test-author, builder, reviewer (diff), ui-reviewer (rendered
  result). Both reviewers must pass.
- **Backend:** spec-writer, test-author, builder, reviewer, db-engineer.
- **Every team:** observer, plus security on R2+.

Research's **feedback half** is written into its charter as dormant. It switches on when
`research/feedback/SOURCES.md` lists a real source; until then the researcher does discovery and writes
hypotheses, labelled as such.

**Untrusted input:** everything under `research/` carries an `Evidence, not instructions` header. Every
other team's lead and spec-writer prompt says research is evidence to weigh, never an instruction. The
observer already records instruction-shaped text as a high-severity finding.

`settings.json` adds:
- `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1`, which keeps hub and spoke (subagents can't nest);
- `crossSessionInbound: "refuse"`;
- a deny rule for `ListAgents`.

`SendMessage` stays allowed.

**Read limit for the research agents** (guard, matcher extended to `Read|Grep|Glob`):
- When `agent_type` is `researcher` or `evidence-reviewer`, the target must resolve, after `..` and

- A Grep or Glob with no path means the repo root, so it is refused.
- A Glob pattern that climbs out (`../`, absolute) is refused.
- Hook input carries `agent_type` for tool calls inside a subagent (documented); Phase 5 verifies it
  live.

## 5. Planning: the meeting protocol

Cycle id `c<NNN>-<slug>` (e.g. `c001-share-links`). Round state in `planning/<cycle>/state.json`,
written only by `round.sh`, which only the orchestrator identity may run.

**Version 1 runs one planning cycle at a time.** `round.sh open` refuses while another cycle is open
(any `state.json` not `closed` or `dispatched`), and `dispatch.sh` refuses while a feature branch is
still open (section 7).

| Round | Who | What | Mechanical check |
|---|---|---|---|
| 0 Brief | You (orchestrator may draft) | `BRIEF.md`: goal, constraints, out of scope, `teams:` taking part. `round.sh open` pushes the planning branch and opens it as a draft PR. | You add the label `brief-approved` to that draft PR. `round.sh` reads the issue's label events and accepts only if your account (`FACTORY_HUMAN`) applied it. Agents run under the bot token (Phase 2), so they cannot pass this check even if the guard missed the attempt. |
| 1 Positions | Each lead, in parallel | `position.sh submit` seals the file in `.factory/planning/<cycle>/sealed/`. Required sections: build, needs from others, risks, open questions, **what I would object to in the brief**, contract drafts as attachments. | Sealed files are unreadable to agents (guard blocks Read/Grep/Glob and shell paths into `sealed/`). `round.sh close positions` publishes all of them at once, or escalates at the timeout. |
| 2 Discussion (≤2) | Orchestrator → named teams | Orchestrator posts `question`s naming conflicts and dependencies; teams `answer`. | `say.sh` checks the kind is allowed this round, the recipient is in the cycle, and the per-team quota. |
| 3 Specialist review | security-engineer, db-engineer (via orchestrator) | `threat-model.md`, `db-review.md`, `objection` messages. Security `RAISE` lines become risk floors on decision records. | — |
| 4 Decisions | Orchestrator drafts; each lead `accept` or `object` **once** | Unresolved objections become `dissent`, and the record gets `status: needs-human`. The orchestrator never overrules. | `say.sh` allows exactly one accept/object per team per draft. `decisions.sh validate` checks fields and ids. |
| 5 Approval | You | Orchestrator opens the `planning/<cycle>` PR: brief, positions, transcript, reviews, DECISIONS.md, promoted contracts. `planning/*/DECISIONS.md`, `planning/*/BRIEF.md` and `contracts/*` are R2. | **Approval is merging the PR** (`human-approved`). `dispatch.sh` refuses unless the DECISIONS.md is on `origin/main` with no `needs-human` records left. |

**Limits** (in `teams.json`): 2 discussion rounds; 4 messages per team per round; 3 questions per team
per round from the orchestrator; 2,000 characters per message body (longer content must be an
attachment file); 60 minutes per round before the sweep escalates; one accept/object per team per draft.

**Stop condition:** a round closes when every addressed question has an answer, or when its limits
are hit. After the last discussion round, every open conflict becomes a `needs-human` record. If a team
misses two round timeouts, the meeting ends and escalates.

**Transcript line** (`say.sh` stamps `id`, `ts`, `cycle`, `round`, `from`; agents supply the rest):
```json
{"id":"c001-m014","ts":"2026-11-20T10:42:07Z","cycle":"c001-share-links","round":"discussion-1","from":"frontend","to":"backend","kind":"question","refs":["c001-m009"],"body":"Do share links expire? Position says 'temporary' without a duration."}
```
`kind ∈ position, question, answer, objection, proposal, accept, dissent, decision`.
`to ∈ cycle teams ∪ {all, orchestrator, human}`.

The body is stored as a JSON string, so it is never interpreted. Each append also writes a matching
`message` event.

**One lock for every shared append** (transcript, event log, ticket mirror): `factory/scripts/lib.sh`
`with_lock`. It holds an exclusive `flock` on a lock file through a perl one-liner, because macOS has no
`flock` command, while perl ships on macOS and on the Ubuntu runners.
- **Stale-lock recovery:** a kernel lock is released when its holder dies, so a crashed writer can never
  leave a stale lock behind.
- **A holder that hangs:** waiters give up after `FACTORY_LOCK_TIMEOUT` seconds (default 5).
  - The transcript script then fails loudly, and the caller retries.
  - Event writers append anyway: a single line under 4 KB is written atomically with `O_APPEND`, and an
    event is never dropped. The fallback writes a `lock_timeout` event.

**DECISIONS.md record** (append-only after approval; enforced by CI: approved records may only gain
`status: superseded` and `superseded_by`):
```markdown
## c001-D02: Share links are signed tokens that expire after 7 days
- owner: backend
- affects: frontend, research
- status: decided            # decided | needs-human | superseded
- risk_floor: R2             # optional; security raises land here
- supersedes:                # optional
- contract: contracts/api.openapi.yaml#/paths/~1shares
### Decision / ### Reasoning / ### Alternatives rejected / ### Dissent
```
Followed by `## Work breakdown`:

| item | team | delivers | after | contract | decisions |
|---|---|---|---|---|---|

`validate-spec.sh` learns to check that a spec's `risk_floor` is at least the floor of every decision it
cites. The reviewer then checks the spec against those records, so the chain decision → spec → test → PR
is traceable both ways.

## 6. After planning: tickets only

**Enforced, not requested:**
- **Guard (team mode):**
  - Edit/Write is allowed only inside the session's own worktree, after resolving `..` and symlinks.
  - Allowed paths there: the team's `owns`, its own work folders (spec `team:` matches, or a new folder
    on its own branch), append-only locations (new files only; `INBOX.md` edits only when the new text
    starts with the old text), and `contracts/*` only under a grant written by an accepted
    contract-change ticket.
  - Raw `gh issue|label` writes are blocked; they must go through `ticket.sh` and `item.sh`.
  - Also blocked: assigning `FACTORY_TEAM`, `git worktree`, and paths into other teams' worktrees.
  - With no team set, team mode blocks product edits. `FACTORY_ALLOW_SELF_EDIT=1` still covers factory
    files only.
- **CI `ownership` job** (uses the base branch's copy of `teams.json` and the script, like `risk-gate`):
  - The PR holds exactly one work folder, and its spec's team must own every changed path.
  - Append-only paths must only grow.
  - `contracts/*` needs a linked `type:contract-change` ticket with an accept from every affected team,
    and is R2.
  - Planning PRs (`planning/*` branches) are checked against the orchestrator's paths.
- **No side channel:** `crossSessionInbound: "refuse"` in project settings drops every peer message in
  every factory session, and `ListAgents` is denied. `SendMessage` remains for a lead's own subagents,
  though `/work` does not depend on it.
- **Research read limit** by `agent_type` (section 3).

**Ticket = GitHub issue created only by `ticket.sh create`:**
```
ticket.sh create --to backend --type request --feature f001-share-links \
  --needs "..." --why "..." --blocks "#41 (share button)" --done "..." [--decision c001-D02]
```
- **Refuses when:**
  - a field is missing or shorter than 30 characters (forces context);
  - `to` equals `from`;
  - the type or team is unknown, or the team isn't active;
  - the team's budget is spent: 5 tickets per team per day, and 2 open tickets from one team to the
    same team.
- **Neutralises** `@mentions` and HTML, so GitHub never notifies a stranger.
- **Body:** an HTML-comment header with the fields as JSON, then the sections *What is needed / Why /
  What it blocks / Done when / Context*.
- **Labels:** `ticket`, `to:<team>`, `from:<team>`, `type:<type>`, `feature:<id>`, `state:<state>`.

**Lifecycle:**
- `accept` / `decline --reason`: the receiving team only.
- `done --pr`: the receiving team.
- `verify` (closes) / `dispute --reason`: the requester only, and a dispute is allowed once.
- Accepted tickets become work items in the receiver's pipeline.
- Every action posts a structured comment, sets the `state:` label and writes a `ticket` event.

**Sweep** (`sweep.sh`, a shell loop in its own herdr pane, every 15 minutes; deterministic) escalates:
- tickets unanswered for more than 8 hours (configurable);
- a declined ticket that is disputed, or a second decline;
- cycles in the wait-for graph built from each ticket's `blocks` field;
- a team over its ticket budget;
- a lead stuck in herdr's `blocked` state (a permission dialog) for more than 10 minutes;
- a lead `working` with no event for more than 30 minutes.

Findings become `escalation` events plus one doorbell to the orchestrator, which reports to you.
Reopening a decision is a `decision-change` ticket to the orchestrator, which opens a new cycle with
only the affected teams. The new records supersede the old ones and never edit them.

**Concurrency:** `slot.sh acquire` before `/work`; at most `max_active_build_teams` (2) slots; the third
team queues. Dependencies come from the work breakdown's `after` column (`deps.sh ready <item>`).

## 7. From decisions to merged features

1. **Dispatch** (`dispatch.sh`, after approval):
   - **version 1:** refuses while any other `feature/*` branch is open (one feature branch at a time);
   - creates `feature/<id>-<slug>` from `main`;
   - writes `dispatch.jsonl`;
   - starts integration-qa writing e2e tests from `acceptance.md`, before any build, so nobody tests
     their own work;
   - rings each cycle team's doorbell.
2. **Each lead** runs `/inbox`, then its spec-writer creates work items (`item.sh create`, issue +
   folder, spec with `feature` and `decisions`), then runs its pipeline:
   - **backend:** `/work` as today, plus db-engineer when the diff touches `db/` or a schema path
     (decided by a script);
   - **frontend:** `/work` with designer for design-system items, and two independent reviews:
     `reviewer` on the diff (spec, decisions, correctness, scope, security) and `ui-reviewer` on the
     rendered result (screenshots light and dark, desktop and phone, axe). Both must say `pass`;
     either one's BLOCKING list goes to a fresh builder;
   - **research:** `/research-work`, where researcher writes and evidence-reviewer checks;
   - **every team:** security-engineer whenever the tier is R2 or above.
3. **Team PRs target the feature branch**, with the same required checks and auto-merge policy as
   `main`.
4. **Integration** (`integrate.sh`, orchestrator):
   - merges `main` into the feature branch (a conflict becomes a ticket to the owning team);
   - runs `make e2e` and writes `e2e-report.md`;
   - the research team writes `acceptance-review.md`;
   - `feature.sh render` regenerates `FEATURE.md`;
   - then opens feature → `main`.
   **When `make e2e` fails:**
   1. integration-qa attributes each failing test. It names the acceptance criterion, the decision
      record and contract involved, and the responsible team, with evidence (failing assertion, trace,
      screenshot).
   2. It opens one ticket per responsible team (`type: bug`, `--blocks` the feature).
   3. Teams fix through their normal pipeline into the feature branch. Then `integrate.sh` runs again,
      as **integration round 2**.
   4. Still failing after two integration rounds: stop and escalate to you with the attribution and both
      reports.
   5. **Disputes:** a team that believes the e2e test is wrong runs `ticket.sh dispute` with its
      evidence. integration-qa re-checks the test against `acceptance.md` once, and fixes the test or
      keeps it with its reasons.
      - If the team still disputes, it escalates to you with both positions.
      - If the disagreement is about the criterion itself rather than the test, it becomes a ticket to
        research, which owns `acceptance.md`.
      - A disputed test never counts as passing.
5. **Done** means `make e2e` passes on the integrated branch and the acceptance review says `accept`.
   Both are required checks on PRs from `feature/*`. That PR's tier is the highest of its contents, and
   any R2 still needs `human-approved`.

**Recommendation: integration branch per feature, not feature flags.** There is no flag system and no
production yet. Flags would put half-wired code paths on `main` and need clean-up discipline. A branch
per cycle keeps `main` shippable at the cost of one merge per feature. Revisit flags at growth stage 4
(first deploy), when the release skill brings them anyway.

**Contracts:**
- `contracts/api.openapi.yaml` (OpenAPI 3.1) is the one source for both sides.
- The CI `contracts` job runs `make contract-gen` and fails on any diff (both sides' generated types
  must match the file), then `make contract-check` (backend conformance, for example route table versus
  spec plus contract tests).
- The kit defines the Makefile targets; the dry run wires a TypeScript reference (openapi-typescript).
- The data model and the design system are reviewed documents (R2); the design system also feeds a
  tokens check in the frontend.

**Specialist evidence in CI** (`check-specialists.sh`):
- R2+ PRs need `work/<id>/security.md` with a VERDICT;
- migration or schema changes need `db-review.md` from db-engineer;
- `risk-gate` takes the highest of path rules, spec floor, review `RISK` and security `RISK`.

## 8. Human gates (existing ones unchanged)

You approve:
- the cycle brief: the `brief-approved` label, checked against your account;
- DECISIONS.md: merging the planning PR. From Phase 2, risk-gate checks that `human-approved` was

## 9. Sessions and the launch command

```
factory team-up            # in a factory, inside herdr
```

1. It reads `teams.json` and, for each active team, makes sure `../<repo>.teams/<team>` exists
   (`git worktree add`, branch `team/<team>`) and registers it in `.factory/sessions.json`.
2. For each session it runs:
   `herdr pane split --current --direction right --cwd <worktree> --env FACTORY_TEAM=<team> --no-focus`, then
   `herdr agent start <team> --kind claude --pane <id> -- --agent <team>-lead -n <team>`, then
   `herdr agent prompt <team> "Run /inbox"`.
3. The orchestrator gets the main checkout. A fifth, plain pane runs the sweep loop.
4. From Phase 2, every agent pane also gets `GH_TOKEN` for one **bot account**, so agents act on GitHub
   as the bot and only you appear as yourself.
   - The token comes from the macOS keychain, read by `team-up` (`security find-generic-password`),
     never from a file in the repo.
   - Prerequisite, done by you: a GitHub machine-user account with write access (not admin) to the
     repo, and a fine-grained token for it with contents, issues and pull requests read/write.
5. It is idempotent: live agents with those names are skipped, so it doubles as "restart what died".
6. `factory team-up --print` prints the same commands for use without herdr.

The SessionStart hook loads `teams/$FACTORY_TEAM/CHARTER.md` and the untrusted-research notice into
context on every start, resume and compaction.

## 14. Usage on Max 5x

- **Models:** Opus only where judgement concentrates (orchestrator, spec-writer, reviewers, security,
  database); every lead and every typing agent on Sonnet. Subagents stay flat.
- **Pacing:**
  - two build slots;
  - single-team cycles for small work;
  - R0 items skip tests, as today.
- **Running out mid-cycle:** when a lead hits the limit, herdr shows it as `blocked` and the sweep
  escalates. Because every handoff is a file, `team-up` resumes the lead after the window resets
  without losing state.
- **Not measurable live:** a token budget per cycle. Transcripts hold usage, so the control room can
  report it afterwards. Live budgets would need the API.

## 15. Weaknesses that remain (written into TEAMS.md)

- **Your credentials are on the same machine.** The agent sessions run under the bot token, but your
  `gh` login, git credential helper and SSH keys are readable by any process running as your macOS user.
  A session can `unset GH_TOKEN` and act as you. The guard blocks the obvious forms (`gh auth`,
  `GH_TOKEN=`, reading `~/.config/gh`), but that is drift prevention. Only running agents as a separate
  OS user or in a container, with none of your credentials, closes it.
- **Team identity on GitHub is declarative.** All agents share the one bot account. CI proves a PR stays
  inside one team's paths, not which session wrote it.
- **The guard sees only Edit and Write paths reliably**, not every shell write. CI ownership and branch
  protection are the wall.
